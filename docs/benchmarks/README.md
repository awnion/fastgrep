# fastgrep versus GNU grep

Last benchmark run: **2026-10-05**.

Measured on an Apple M2 Max (12 logical CPUs), 32 GB RAM, macOS 27.0.1
(26A434). fastgrep 0.1.9 was built from commit `5094623` using Rust 1.99.0
(`b940084d7`, 2026-09-28), with the repository's release profile
(`opt-level = "s"`, LTO, one codegen unit, stripped binaries). GNU grep is
Homebrew's `ggrep` 3.12. Both runs used `LC_ALL=C` and default thread counts.

## Comparison

The deterministic Rust-like corpus is generated by
[`benches/corpus.rs`](../../benches/corpus.rs). Main recursive workloads use
200 files × 5,000 lines (one million lines total); the single-file workload uses
100,000 lines. Scaling workloads use 2,000 lines per file.

```text
+---------------------------------------+-----------+------------+----------+---------+
| Workload                              | fastgrep* | --no-index | GNU grep | GNU/fg* |
+---------------------------------------+-----------+------------+----------+---------+
| -rn "fn main" (sparse)                |   8.82 ms |    7.31 ms | 32.99 ms |   3.74x |
| -rl "fn main"                         |   7.50 ms |    5.88 ms |  7.12 ms |   0.95x |
| -rc "use " (dense)                    |   8.55 ms |    7.64 ms | 84.75 ms |   9.91x |
| -rni "error"                          |  37.49 ms |          - | 82.57 ms |   2.20x |
| -rn impl\s+Drop                       |  45.24 ms |   35.31 ms | 73.43 ms |   1.62x |
| -rn SubscriptionManager (very sparse) |   5.41 ms |    6.30 ms | 39.35 ms |   7.28x |
| Single file (100k lines)              |   3.70 ms |          - |  5.21 ms |   1.41x |
+---------------------------------------+-----------+------------+----------+---------+
```

Scaling (2,000 lines per file):

```text
+-------+-----------+------------+----------+---------+
| Files | fastgrep* | --no-index | GNU grep | GNU/fg* |
+-------+-----------+------------+----------+---------+
| 50    |   4.17 ms |    3.43 ms |  6.17 ms |   1.48x |
| 200   |   7.02 ms |    5.70 ms | 17.07 ms |   2.43x |
| 500   |  12.50 ms |    9.65 ms | 38.49 ms |   3.08x |
+-------+-----------+------------+----------+---------+
```

`fastgrep*` uses a warm index where applicable. `--no-index` is the fastgrep
variant with indexing disabled. The ratio is GNU grep time divided by
fastgrep's default time. Values above 1 mean fastgrep is faster; below 1 mean
GNU grep is faster. For case-insensitive
search, the index is bypassed; single-file search does not use an index. The
separate `--no-index` variant is not provided by the harness for those two rows.

## Method

The existing Criterion 0.8.2 suites ran sequentially: fastgrep first, then GNU
grep. Each benchmark has a 3-second warmup and a 5-second target measurement
period; Criterion can extend the period for slower queries. Main workloads use
100 samples; scaling uses 10. Times above are Criterion's central estimates
(mean for flat sampling, regression slope for linear sampling), rounded to two
decimal places. Ratios are calculated from unrounded estimates.

Each timed iteration launches a subprocess and captures stdout and stderr in
memory using `Command::output()`. The measurements include process startup,
search, and output capture; output is not redirected to `/dev/null`. GNU grep
uses basic regex syntax, so its regex query is `impl\s\+Drop`, equivalent to
fastgrep's `impl\s+Drop`.

The fastgrep index is populated before timing indexed literal and regex queries.
First-search index construction is excluded. Filesystem pages are not evicted:
these are warmed filesystem measurements, not cold disk I/O. Only benchmark
subprocesses were given a temporary home/cache directory, isolating the index
from the user's cache. The shell and build environment were retained.

The seven query types were also checked on a smaller corpus generated with the
same line patterns: sorted output matched GNU grep for both indexed and
`--no-index` searches. Sorting accounts for parallel output order.

These results describe this generated corpus on this machine. All files contain
`fn main`, `use `, and `impl Drop`; the index cannot exclude files for those
patterns. Only every tenth file contains `SubscriptionManager`. Index metadata
checks can add overhead when almost every file must be searched. Scaling ratios
compare absolute search time at each file count; they do not establish a general
claim about asymptotic scaling.

## Reproduce

On macOS, install GNU grep (`brew install grep`) and use `ggrep`, since
`/usr/bin/grep` is BSD grep. On Linux, use the path to GNU grep instead.

```sh
cargo build --locked --release --bins
LC_ALL=C cargo bench --locked --bench grep_bench -- --noplot
LC_ALL=C BASELINE_GREP=ggrep cargo bench --locked --bench baseline_bench --features baseline -- --noplot
```

`grep_bench` clears fastgrep's trigram cache between indexed benchmark groups.
For cache isolation, build first and run the compiled benchmark executables with
a temporary `HOME`, retaining the original `CARGO_HOME`, `RUSTUP_HOME`, and
`CARGO_TARGET_DIR` for binary discovery. The executable paths are printed by
`cargo bench --no-run`.
